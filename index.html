GitHub, Supabase e migrations: estrutura versionada para estudar SQL e PostgreSQL

Projeto atual PostgreSQL Supabase Migrations Git e GitHub pgAdmin 4
Usei inteligência artificial como apoio para consultar comandos e revisar alternativas, mas mantive sob minha responsabilidade a execução, a interpretação dos erros, a correção do ambiente e a validação do estado local e remoto do banco de dados.

Por que criei este projeto

Criei o repositório transicao-database-supabase para funcionar como meu laboratório de atualização em SQL e PostgreSQL. A intenção não é apenas armazenar consultas isoladas, mas desenvolver os próximos exercícios sobre uma estrutura reproduzível, versionada e capaz de registrar a evolução do banco de dados.

O projeto combina GitHub, Supabase, PostgreSQL, Supabase CLI e pgAdmin 4. Nesse fluxo, a estrutura do banco é descrita por arquivos de migration mantidos no repositório. Assim, cada alteração relevante pode ser revisada, aplicada e conferida, em vez de existir somente como uma mudança manual no painel do banco.

Fluxo que eu pretendia estabelecer

  1. Manter o código e as migrations em um repositório Git.
  2. Associar o ambiente local a um projeto remoto no Supabase.
  3. Criar alterações no banco por migrations SQL.
  4. Registrar cada etapa por commits e enviar para o GitHub.
  5. Verificar se as migrations locais e remotas representam o mesmo estado.
  6. Usar o ambiente como base para exercícios futuros de SQL, modelagem e PostgreSQL.

1. Repositório, projeto remoto e conexão inicial

O primeiro passo foi criar o repositório no GitHub, cloná-lo para o computador e passar a trabalhar no diretório versionado. Em paralelo, criei minha conta no Supabase e um projeto de banco de dados do zero.

Também configurei uma conexão pelo pgAdmin 4. Nessa etapa, informei inicialmente o host com o prefixo http://. A conexão falhou porque o campo de host espera o nome do servidor, não uma URL HTTP. Após remover o prefixo e usar corretamente o endereço do banco e a senha, a conexão foi estabelecida.

Para confirmar que eu estava conectado ao servidor PostgreSQL correto, executei:

SELECT version();

2. Erros de autenticação e recuperação de acesso

Durante os testes, errei a senha algumas vezes e meu endereço IP foi bloqueado temporariamente. Em vez de tratar o erro apenas como uma falha genérica de conexão, consultei o painel do projeto, removi o bloqueio do IP e redefini a senha do banco na área de configurações.

Esse episódio ajudou a separar três causas diferentes que podem produzir sintomas semelhantes: host informado incorretamente, credencial inválida e bloqueio temporário por tentativas repetidas.

3. Inicialização da CLI e comandos auxiliares

Com apoio de IA, organizei atalhos no package.json para reduzir erros de digitação e tornar os comandos mais previsíveis durante os estudos. Antes de utilizá-los, conferi o que cada comando executava e mantive os nomes alinhados às ações da CLI.

"scripts": {
  "supabase:init": "supabase init",
  "supabase:login": "supabase login",
  "supabase:link": "supabase link",
  "migration:new": "supabase migration new",
  "migration:list": "supabase migration list",
  "db:start": "supabase start",
  "db:stop": "supabase stop",
  "db:reset": "supabase db reset",
  "db:pull:transicao": "supabase db pull --schema transicao",
  "db:push:check": "supabase db push --dry-run",
  "db:push": "supabase db push"
}

Depois de inicializar a estrutura, fiz um commit antes de começar as migrations. Isso criou um ponto de referência para diferenciar a configuração inicial das alterações posteriores do banco.

git add .
git commit -m "chore: inicializa projeto Supabase"

4. O uso inadequado de db pull e o que aprendi

Executei supabase db pull --schema transicao antes de existir qualquer objeto no banco remoto. Durante o processo, a CLI baixou imagens Docker usadas por suas ferramentas locais. Inicialmente, aquele volume de downloads poderia ser confundido com o conteúdo do banco, mas compreendi que eram componentes de apoio da própria CLI.

Como o schema transicao ainda não existia, não havia uma estrutura remota para transformar em migration local. O comando não era necessário naquele ponto do fluxo. O db pull faz mais sentido quando o banco remoto já contém objetos que precisam ser capturados como referência para o histórico local.

Decidi excluir e recriar o projeto para repetir a configuração desde o início. Essa recriação não era uma exigência técnica para todo projeto, mas foi útil como exercício de fixação e permitiu refazer conscientemente cada etapa.

5. Integração entre GitHub e Supabase

Após reconstruir o ambiente, configurei a integração do projeto Supabase com o repositório do GitHub e associei a branch main. A partir daí, as migrations passaram a fazer parte do mesmo fluxo de versionamento adotado para o restante do projeto.

O ponto importante não era apenas ativar uma integração visual no painel. Eu precisava conferir se uma alteração criada localmente, registrada no Git e enviada ao repositório apareceria efetivamente no banco remoto.

6. Primeira migration: criação do schema

Criei a primeira migration com um nome que expressa a alteração realizada:

npm run migration:new -- create_transicao_schema

No arquivo gerado, defini a criação do schema transicao. Em seguida, executei git add, git commit e git push.

Não considerei a migration concluída apenas porque o comando terminou sem erro. Verifiquei o resultado por caminhos independentes:

  • consulta ao schema pelo painel do Supabase;
  • consulta SQL ao catálogo do PostgreSQL;
  • inspeção do banco pelo pgAdmin 4;
  • comparação do histórico local e remoto pela CLI.
select schema_name
from information_schema.schemata
where schema_name = 'transicao';

Também executei npm run migration:list e confirmei que a migration aparecia tanto no histórico local quanto no remoto.

7. Segunda migration: tabela de exemplo

Depois de validar a criação do schema, criei outra migration para adicionar uma tabela simples. O objetivo era testar uma evolução real do banco, incluindo chave primária gerada automaticamente, campos obrigatórios, unicidade e valor padrão de data e hora.

create table transicao.usuario (
  id bigint generated always as identity primary key,
  nome text not null,
  email text not null unique,
  criado_em timestamptz not null default now()
);

Novamente, registrei a alteração no Git, enviei ao GitHub e conferi o histórico com npm run migration:list. A presença da migration nos estados local e remoto confirmou que o fluxo continuava consistente após uma segunda alteração.

O que demonstra que eu sabia o que estava fazendo

O uso de IA não eliminou a necessidade de compreender o ambiente. Ao longo da tarefa, precisei distinguir conceitos e estados diferentes:

  • host de banco de dados não é uma URL HTTP;
  • falha de senha e bloqueio temporário de IP são problemas distintos;
  • download de imagens Docker pela CLI não significa download dos dados do banco;
  • db pull e criação de uma nova migration atendem a situações diferentes;
  • um arquivo presente no Git não prova, sozinho, que a alteração foi aplicada no banco;
  • o histórico local e o histórico remoto de migrations precisam ser comparados;
  • a validação deve incluir consultas ao catálogo, painel e cliente externo quando possível.

A IA foi útil para acelerar consultas, revisar comandos e organizar alternativas. Ainda assim, as decisões, a execução, a leitura dos erros e a comprovação dos resultados permaneceram sob minha responsabilidade.

Como esta estrutura será utilizada

Este repositório será a base dos meus projetos de retomada de SQL e PostgreSQL. Pretendo evoluir o banco por migrations pequenas e identificáveis, acrescentando progressivamente tabelas relacionadas, restrições, índices, dados fictícios de teste, views e consultas de relatório.

Esse formato permite estudar não apenas a sintaxe SQL, mas também práticas de trabalho: histórico de alterações, reprodutibilidade, revisão, separação entre configuração e evolução do banco, documentação dos erros e validação em mais de uma ferramenta.

Segurança e proteção de dados

O projeto é exclusivamente educacional e de portfólio. As próximas cargas e arquivos de seed deverão utilizar somente dados fictícios, públicos ou adequadamente anonimizados. Senhas, tokens e configurações locais não devem ser versionados.

Antes da publicação de novas etapas, o projeto deverá receber o checklist curto de segurança, LGPD, riscos técnicos e riscos essenciais relacionados ao OWASP, conforme o padrão adotado no meu roadmap.

Próximos passos

  • documentar os requisitos do primeiro modelo de dados demonstrativo;
  • criar migrations menores para tabelas, relacionamentos e restrições;
  • adicionar um arquivo de seed apenas com dados fictícios;
  • praticar SELECT, JOIN, GROUP BY, CTE, views e índices;
  • registrar testes de aplicação e reconstrução do banco;
  • criar e preencher o checklist essencial de segurança antes de concluir o projeto.

Resultado

Ao final da tarefa, o projeto ficou criado e versionado, o banco PostgreSQL remoto estava acessível pelo pgAdmin 4, a integração com o GitHub estava configurada e duas migrations haviam sido verificadas local e remotamente: uma para o schema transicao e outra para a tabela de exemplo usuario.

Mais do que configurar uma ferramenta, a atividade estabeleceu a infraestrutura que utilizarei para transformar os próximos estudos de SQL e PostgreSQL em alterações rastreáveis, reproduzíveis e publicamente verificáveis.

Política de Privacidade

Versão de 08/08/2026. Esta política descreve, de forma proporcional ao funcionamento atual do site, quais dados podem ser tratados durante a navegação e quais controles são adotados.

Resumo: o código deste site não possui cadastro, formulário próprio de coleta, publicidade, ferramenta própria de analytics, pixel de marketing ou mecanismo próprio de perfilização. O provedor de hospedagem, KingHost/LWSA, pode processar dados técnicos necessários à entrega, segurança e operação do serviço, inclusive endereço IP e registros de navegação, conforme seus contratos e política de privacidade.

1. Responsável e canal de contato

O daniel.fleck.dev.br é um site pessoal e profissional mantido por Daniel Rodrigo Fleck. Para assuntos relacionados a privacidade, proteção de dados, correção de informações ou exercício de direitos, o canal de contato disponibilizado é contato@fleck.dev.br.

Quando houver tratamento de dados pessoais determinado diretamente pelo responsável pelo site, esse tratamento será limitado às finalidades necessárias ao funcionamento, segurança, exercício de direitos e atendimento de obrigações aplicáveis. A KingHost/LWSA pode atuar no tratamento de dados conforme o papel definido no serviço contratado e em sua própria Política de Privacidade.

2. O que este site não coleta intencionalmente

  • não existe cadastro de usuários ou área de login;
  • não existe formulário próprio para coleta de nome, CPF, telefone, endereço ou outros dados pessoais;
  • o código do site não cria cookies próprios de publicidade ou rastreamento;
  • não há Google Analytics, Meta Pixel ou ferramenta própria de analytics comportamental;
  • não é criado banco de dados próprio com histórico de visitantes;
  • não há venda, compartilhamento comercial ou criação de perfis de visitantes para publicidade.

O endereço de e-mail profissional exibido no próprio site é informação disponibilizada voluntariamente pelo responsável como canal público de contato.

3. Dados técnicos tratados pela infraestrutura de hospedagem

O site é hospedado na KingHost, integrante da LWSA. A infraestrutura de hospedagem pode registrar ou processar automaticamente informações necessárias à entrega e proteção do serviço. A Política de Privacidade da LWSA informa que, em interações com serviços de seus clientes, podem ser tratados dados como endereço IP, sistema operacional, informação de geolocalização, identificadores do dispositivo e dados de navegação, incluindo datas de uso e páginas visualizadas.

A KingHost também disponibiliza recurso administrativo de estatísticas que pode apresentar, entre outros elementos, IPs de visitantes, país, duração das visitas, páginas acessadas, sistema operacional, navegador e erros HTTP. Esse recurso, quando disponível, deve permanecer protegido por autenticação e não deve ser exposto publicamente.

Importante: afirmar que “nenhum IP é tratado” seria incorreto. O código do site não mantém cadastro próprio de IPs, mas a infraestrutura de hospedagem pode processar registros técnicos.

4. Finalidades e minimização

Dados técnicos eventualmente tratados pela infraestrutura podem ser necessários para disponibilização do conteúdo, segurança, prevenção de abuso, diagnóstico de falhas, suporte, estatísticas técnicas e cumprimento de obrigações legais ou contratuais. O responsável pelo site não utiliza esses registros para publicidade comportamental, venda de dados ou formação de perfis comerciais.

Se for necessário consultar informações de acesso para investigar falha ou incidente de segurança, o uso deverá ser restrito ao necessário para essa finalidade, com acesso administrativo limitado e observância dos princípios de finalidade, adequação, necessidade e segurança.

Não é apresentado banner de “aceite de cookies” porque o código atual não utiliza cookies próprios não essenciais nem solicita consentimento para rastreamento. Caso o site passe a incorporar analytics, formulários, publicidade ou outra tecnologia de coleta, esta política deverá ser revisada antes da ativação.

5. Armazenamento, retenção e acesso

O responsável pelo site não mantém, por iniciativa própria, uma base separada com histórico de navegação de visitantes. Os registros técnicos existentes na infraestrutura seguem os mecanismos e prazos do provedor. A Política de Privacidade da LWSA informa que dados pessoais podem ser mantidos pelo tempo exigido por lei, até o término da finalidade do tratamento ou pelo período necessário à preservação de interesses legítimos e exercício de direitos, observada a legislação aplicável.
