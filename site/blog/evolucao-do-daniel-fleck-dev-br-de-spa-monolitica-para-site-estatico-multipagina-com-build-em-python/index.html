Evolução do daniel.fleck.dev.br: de SPA monolítica para site estático multipágina com build em Python

Reestruturação do site estático com URLs próprias para blog, portfólio, erros, tags e páginas, além de scripts Python automatizando conteúdo, rebuild, validação, sitemap e pré-commit.

PythonHTMLJavaScriptCSSIAsupervisão humana

Contexto

Contexto

O daniel.fleck.dev.br nasceu como uma aplicação de página única desenvolvida com HTML, CSS e JavaScript. Blog, portfólio, currículo resumido, ferramentas, documentos institucionais e outros conteúdos eram concentrados principalmente em um único index.html, com JavaScript responsável por alternar as seções exibidas ao visitante.

Essa abordagem foi adequada para a primeira versão do projeto: permitiu desenvolver e publicar rapidamente um site sem framework, backend ou banco de dados. Com o crescimento do conteúdo, porém, o arquivo principal passou a concentrar muitas responsabilidades.

Posts do blog, itens do portfólio, registros da Base de Conhecimento — Erros e Soluções, tags, metadados para mecanismos de busca e diversos elementos de navegação passaram a compartilhar a mesma estrutura. A manutenção continuava possível, mas exigia cada vez mais cuidado para manter referências e representações sincronizadas.

Problema de arquitetura

O principal problema não era o uso de HTML, CSS ou JavaScript puro. Essas tecnologias continuam adequadas para o projeto. O ponto a ser revisto era a concentração de conteúdos independentes dentro de uma única página.

Um artigo de blog, por exemplo, deveria poder possuir sua própria URL, título, descrição, canonical e dados estruturados. O mesmo vale para um item de portfólio ou para o registro de um erro conhecido.

A arquitetura anterior utilizava referências internas semelhantes a: 

daniel.fleck.dev.br/#post-identificador

Na nova estrutura, cada conteúdo relevante passa a possuir uma página HTML real, como: 

daniel.fleck.dev.br/blog/evolucao-site-estatico-multipagina-python/

daniel.fleck.dev.br/portfolio/...

daniel.fleck.dev.br/erros/...

Decisão: continuar com um site totalmente estático

A mudança não introduziu CMS, banco de dados, backend ou framework JavaScript. A hospedagem continua recebendo apenas arquivos estáticos.

O resultado publicado continua sendo composto essencialmente por:

  • HTML;
  • CSS;
  • JavaScript;
  • imagens e demais arquivos estáticos.

O Python foi introduzido somente no ambiente de desenvolvimento. Ele não é necessário para atender uma requisição do visitante e não precisa ser executado pela hospedagem.

A ideia foi manter a simplicidade operacional do site estático e utilizar Python apenas para automatizar tarefas que anteriormente precisariam ser feitas manualmente.

Nova organização do conteúdo

Os principais tipos de conteúdo passaram a ter diretórios próprios. 

/

│   └── <slug-do-post>/
│       └── index.html
│
├── portfolio/
│   ├── index.html
│   └── <slug-do-projeto>/
│       └── index.html

A página inicial passa a atuar principalmente como um hub para apresentação, conteúdos em destaque, portfólio, blog, Base de Conhecimento e navegação.

URLs próprias e SEO

Uma das motivações da reorganização foi melhorar a relação entre conteúdo e URL. Cada post agora pode possuir elementos de SEO específicos.

Entre eles:

  • <title> próprio;
  • meta description específica;
  • URL canonical;
  • dados estruturados JSON-LD;
  • tags relacionadas;
  • entrada individual no sitemap.xml.

Isso também torna os links mais compreensíveis para pessoas e mecanismos de busca, porque a própria URL identifica a área e o conteúdo acessado.

Templates para novos conteúdos

Para evitar a cópia manual de páginas antigas, foram criados templates independentes: 

templates/
├── blog.html
├── portfolio.html
└── erro.html

Cada tipo possui estrutura e metadados adequados à sua finalidade.

Um novo conteúdo é criado pelo script: 

python scripts/create_content.py blog

python scripts/create_content.py portfolio

python scripts/create_content.py erro

O script pergunta os principais metadados e cria automaticamente o diretório e o index.html correspondente.

Metadados no próprio HTML

Optei por não criar um arquivo JSON de conteúdo que precisasse ser mantido manualmente em paralelo às páginas.

As informações necessárias para o processo de build ficam junto do próprio documento, em uma área de metadados prevista no template.

Dessa forma, o HTML individual continua sendo a referência do conteúdo, enquanto os scripts conseguem descobrir automaticamente título, resumo, data, categoria, tags e demais atributos necessários para montar os índices.

Rebuild automático

O script central de manutenção é: 

python scripts/rebuild.py

Ele percorre os conteúdos do site e reconstrói somente aquilo que depende deles.

Entre os elementos gerados ou atualizados estão:

  • índice do blog;
  • índice do portfólio;
  • índice de erros e soluções;
  • cards da página inicial;
  • páginas de tags;
  • nuvem de tags;
  • metadados de SEO;
  • JSON-LD;
  • sitemap.xml;
  • robots.txt.

O rebuild foi desenvolvido para ser idempotente: se nenhuma informação tiver mudado, executá-lo novamente não deve produzir modificações desnecessárias.

Nuvem de tags gerada a partir do conteúdo real

As tags não precisam ser mantidas em um catálogo separado.

Durante o rebuild, os scripts percorrem os metadados dos posts do Blog, itens do Portfólio e registros da Base de Conhecimento, contam as ocorrências e geram a estrutura de tags.

Assim, uma tag utilizada em diversos conteúdos recebe maior peso visual na nuvem, enquanto uma tag pouco utilizada aparece proporcionalmente menor.

Também são criadas páginas estáticas específicas, por exemplo: 

/tags/github/
/tags/python/
/tags/postgresql/

Cada uma reúne links para conteúdos relacionados àquele assunto.

Validação antes da publicação

Outro script importante é: 

python scripts/validate.py

Ele executa verificações antes da publicação, procurando problemas como:

  • metadados ausentes;
  • slugs duplicados;
  • links internos inválidos;
  • recursos locais inexistentes;
  • canonical incorreto ou ausente;
  • JSON-LD inválido;
  • placeholders de template ainda presentes;
  • artefatos de build desatualizados.

Servidor local para conferência

Para conferir o resultado antes do commit, o projeto possui um servidor HTTP local baseado somente na biblioteca padrão do Python: 

python scripts/serve.py

Com ele, o site pode ser revisado em: 

http://127.0.0.1:8000/

Isso permite conferir visualmente navegação, CSS, JavaScript, páginas de conteúdo, tags e links antes de publicar.

Proteção no processo de commit

Para reduzir a possibilidade de enviar ao Git um site parcialmente reconstruído, foi criado um hook pre-commit.

A configuração local é feita uma vez com: 

python scripts/install_hooks.py

Durante um commit, o hook executa o rebuild e a validação.

Se o rebuild detectar que algum arquivo precisava ser atualizado, o commit é interrompido. A alteração gerada precisa ser revisada e adicionada conscientemente antes de uma nova tentativa.

Essa decisão evita utilizar git add automaticamente dentro do hook.

Manutenção e apoio de IA

Como o site passou a possuir várias páginas independentes, também foi necessário considerar como uma IA poderá analisar o projeto completo sem depender do envio manual de dezenas de arquivos.

Para isso foi criado: 

python scripts/package_for_ai.py

O script gera: 

dist/site-for-ai.zip

Esse pacote reúne o código e os documentos relevantes para uma análise global, excluindo diretórios locais e artefatos desnecessários.

Além disso, os HTMLs e a documentação do projeto contêm instruções de manutenção para indicar quais regiões são editáveis, quais são geradas automaticamente e quais alterações exigem rebuild de outros arquivos.

Fluxo de trabalho resultante

Para uma alteração comum, o processo passou a seguir aproximadamente esta sequência: 

ativar .venv
        ↓
editar conteúdo ou código
        ↓
python scripts/rebuild.py
        ↓
python scripts/validate.py
        ↓
python scripts/serve.py
        ↓
git diff
        ↓
git add
        ↓
git commit
        ↓
pre-commit valida novamente
        ↓
git push
        ↓
deploy

Resultado

A nova estrutura mantém a característica que considero importante para este projeto: o site continua simples de publicar e servir.

A diferença é que a simplicidade da infraestrutura deixou de significar concentração de todo o conteúdo em um único documento.

O site agora combina:

  • páginas HTML independentes;
  • URLs permanentes por conteúdo;
  • melhor separação entre Blog, Portfólio e Base de Conhecimento;
  • tags com páginas próprias;
  • sitemap gerado automaticamente;
  • validação local;
  • automação do processo de manutenção;
  • publicação final totalmente estática.

A mudança representa uma evolução do projeto sem abandonar sua premissa inicial: utilizar tecnologias simples, compreender o funcionamento do que está sendo publicado e automatizar apenas as tarefas em que a automação reduz erros e trabalho repetitivo.
